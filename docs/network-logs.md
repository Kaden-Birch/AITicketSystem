# UniFi network events and AI evidence

AITicketSystem includes an independent syslog collector and a searchable **Network events** workspace. Migration 41 adds source settings and manual MAC associations; migration 42 adds background archive jobs; migration 43 adds recurring-pattern rules and ticket-scoped AI archive searches. The separate `network-logs` Docker volume contains local history and the upload queue; it is mounted read-only by the main application. Log collection never authorizes remediation. Optional pattern and collection-health rules create tickets through the existing policy engine. Existing maintenance and host permission checks are unchanged. Manual troubleshooting remains available during maintenance.

## Connect a console

1. Update the application:
   ```sh
   cd /opt/aiticket
   git pull --ff-only origin main
   sudo docker compose up -d --build
   ```
2. In `/opt/aiticket/.env`, set `AITICKET_SYSLOG_BIND_ADDRESS` to **the AITicketSystem server's LAN IP**, then run `sudo docker compose up -d --build` again. The default is loopback. The new `log-receiver` service publishes UDP and TCP port **5514**; the application HTTP port is unchanged.
3. Open **Settings → Network logs**, add the actual sending console IP, and select its saved UniFi connection. Each sender IP is unique. Disabled or unknown sources are dropped. Changes apply within five seconds.
4. In UniFi Network, open **Integration → System Logging / SIEM**, select **SIEM Server**, choose event categories, and enter the AITicketSystem server's LAN IP and **5514**. Allow that port from the sender through your server firewall. No API key or certificate setup is needed for this syslog receiver.
5. Generate a client connection/disconnection event. The source's **Last received** time should update; open **Network events** to inspect it. If the sender arrives through NAT, use the actual source IP visible to the receiver. UDP/TCP source-IP allowlisting does not authenticate content. Collection is for trusted LAN senders; there is no TLS syslog endpoint in this release.

Ubiquiti's [System Logs & SIEM Integration documentation](https://help.ui.com/hc/en-us/articles/33349041044119-UniFi-System-Logs-SIEM-Integration) describes its CEF export and event fields. Exact events and available fields depend on UniFi version and selected categories. Old unstructured syslog is retained as generic messages, with coverage shown in Settings.

## Search and association

Search by host, source, severity, event time range, event/message, client IP or MAC. Pages hold 25 events, with at most 10,000 offset rows; narrow a large search to continue. Event details preserve a redacted source message and structured fields. Reported Wi-Fi airtime, interference, signal and channel have compact readouts, explicitly marked **at event time**. These are historical observations, not a continuous airtime measurement or verified current port topology. Source event severity is displayed, not converted into ticket thresholds.

A unique client MAC match in host interface inventory associates the event with that host. Duplicate MAC matches remain unassigned. Without a MAC, an IP match requires a unique interface address observed within three minutes of the event, a usable reported timestamp, and event time within three minutes of receipt. Delayed IP-only events cannot inherit today's address owner. An absent/unusable timestamp uses receipt time with an explicit label; classic syslog's missing year/timezone is not guessed. The CEF `UNIFIutcTime` field is used when it supplies an ISO timestamp and the envelope does not. ISO timestamps outside 31 days of receipt also fall back to receipt time.

A device MAC match is restricted to the source's selected UniFi connection and associates the affected AP/switch independently. The sending console is also recorded. An admin can associate a client MAC from an event's detail page; this mapping overrides automatic client matches for that source and applies immediately to retained history. Select **Use automatic matching** to remove it. It does not alter host interface configuration or confirmed network links. Bindings use MAC identity, so random/private MAC changes need a new association.

Host, UniFi device and ticket pages now show a compact **Troubleshooting timeline**, with a link to a filterable combined view. It combines local network events, monitoring result transitions, resource readings and changes of at least ten percentage points, observed configuration/version changes and ticket activity. Repeated monitoring results are collapsed. Resource comparisons reset after gaps; these presentation rules do not change monitoring thresholds or ticket logic. The full view shows up to 80 entries across up to 16 explicitly related hosts and a maximum 31-day window and labels bounded scans and unavailable sources. Current explicit dependencies and confirmed/corroborated network relationships expand its scope; these relationships do not prove historical topology or causation. Older SMB history remains available through the dedicated archive search.

On UniFi equipment pages, click a port to inspect its API-reported client attachments alongside dated connection/disconnection events. API snapshot age and partial collection are shown separately from historical observations. An attachment can represent a forwarding path through a hypervisor rather than direct physical cabling. AP pages add a selectable event window and sparse signal, airtime and interference charts; hover or use arrow keys for the exact recorded value and time. Missing measurements stay absent, and roaming measurements remain attached to the correct old/new AP. Event counts describe the bounded loaded observations, not all traffic or a continuous performance measurement. Port state and monitoring decisions continue to use existing logic.

 Event time is compared with currently configured maintenance schedules to show a maintenance badge; this is contextual evidence, not an immutable audit of historical policy edits.

## AI usage

Initial investigation snapshots include a small event extract around the ticket's latest failure observation, prioritizing its host, grouped targets, explicitly linked upstream network devices and related hosts (at most eight hosts / five events, about 2,600 characters of event data). Missing logs never establish health or causality.

Hermes can request `aiticket_host` with `action: evidence`, `source: network_logs`, an allowed affected `machine_id`, `offset` and `limit`. This reuses existing target authorization and read-only evidence policies. Results exclude the duplicate raw message, are redacted and bounded to 50 records / 50,000 item characters, and include pagination and maintenance context. The read-only `troubleshooting` evidence source provides the combined local chronology for the authorized host, with the same item/character limits and seven-day window; it does not expand AI target permissions or query SMB. Update/restart the Hermes companion to advertise the new source; tool-free mode receives the initial snapshot. External log text is explicitly untrusted and cannot override instructions, host permissions or maintenance controls.

AI can also retrieve `source: network_problems` for the authorized host. For older history, use `action: archive_search`, optional authorized affected `machine_id`, explicit timezone-bearing ISO `start` / `end`, and an optional query of up to 200 characters. It returns a search ID; poll `action: archive_status` with that ID and the same target. Searches run in the archiver, with at most four searches per AI run, four queued searches across all callers, 31 days per search, 25 batches, 10,000 scanned records, 50 results, a 30-second search timeout and a 16,000-character event budget. Catalog work has its separate bounded worker timeout. Partial results are labelled. Authorization is checked again before archive work and result retrieval; credentials never reach AI. Cache expiry, worker errors and unreadable caches remain distinct from empty results. Tool-free mode does not gain follow-up calls.

Results separate observed facts and event references from suspected causes, which are initially empty. AI can compare recurring findings with existing Knowledge Base articles, optionally create a useful article, or reuse an existing workflow through its existing prerequisites and permission checks. Articles are optional; archive evidence never changes execution permissions. Restart/update the Hermes companion to advertise the added tool actions.

## Recurring problems and shared incidents

Open **Network events → Network problems** to add or edit rules for repeated disconnects, port flapping, device restarts, WAN failovers or authentication failures. Configure a source (or all enabled sources), count, window, severity, enablement and whether to open tickets. Rules default to disabled/evidence-only when added. Pausing a rule preserves existing tickets and stops new automatic admission when all ticket sources are disabled pattern/health checks; explicit manual troubleshooting remains available. They evaluate every 30 seconds. Exact supported CEF names are listed; different UniFi versions may require exact-name overrides from collected events. Unstructured messages and ambiguous device/client identities remain searchable without speculative classification.

Disconnect/authentication rules group by sender, device and client MAC. Port flapping requires alternating up/down observations for the same sender/device/port; repeated identical down messages are not extra transitions. Restart/WAN patterns require a device MAC. Each problem shows current-window count, observed span, affected hosts and recent event references. Disconnect/authentication tickets target the matched client first; device/port patterns target matched infrastructure first, with the console as a fallback. Each uses the selected target’s permissions. Host association changes cannot reuse another host’s check. Maintenance events and currently maintained targets are excluded, including explicit parent scope. A recent matched pattern can open one monitored ticket through existing maintenance, notification, AI admission and remediation policies. Delayed/old events cannot open new automatic tickets. Quiet or expired patterns become unknown, never verified recovery; use independent diagnostics or explicitly resolve the ticket after verification. A quiet pattern does not block verified recovery of an unrelated ticket.

Evaluation inspects the latest 5,000 local events within 24 hours, at most 30 rules, 200 identities per rule and 1,000 retained problems. Limits/unavailable scans are visible. Counts from partial scans are lower bounds. Completed inactive bookkeeping expires after 30 days; saved incident histories remain. Pattern evaluation uses local history, while AI can separately search older SMB evidence.

In **Coverage & health**, enable shared-switch correlation to group current compatible reachability failures on different hosts through a fresh, confirmed or corroborated network path. Similar timing, names, IP proximity or candidate links alone do not group tickets. The resulting investigation retains independent recovery, manual exclusions, host maintenance and original command targets. Shared impact is evidence; it does not establish a failed switch as the cause. This feature is recurring operational detection, not a full threat-detection SIEM.

## Coverage and actionable collection health

Open **Network events → Coverage & health** for matched hosts/roles, sources and last receipt times, events without client matches (and wholly unassigned counts), recognized types/formats, receiver drops/storage errors and SMB pending copies, buffer size, waiting local records and archive gaps. Counts describe the bounded 24-hour scan and current receiver process, not lifetime totals. Quiet sources and hosts without events are never marked unhealthy.

To enable collection-health tickets, choose the application server’s registered host and a persistent-failure duration (default 15 minutes, configurable 2–1,440). The worker monitors receiver heartbeat loss, repeated local storage failures and persistent SMB upload failures with backlog or archive-worker contact loss. Tickets include diagnostic guidance and use that host’s existing maintenance, notification and AI policies. Fresh service evidence is required for recovery. Pausing the SMB archive pauses its health check; removing all enabled senders pauses receiver-contact checks. Configuration/collection failures remain independent of whether a source happens to send messages.

## Collector limits and operation

The receiver supports newline-delimited TCP and RFC6587 octet-counted frames, plus UDP datagrams. It caps each message at 16 KiB, TCP connections at 32, idle TCP lifetime at 30 seconds, sources at 32, and ingestion at 100 messages/second per source with a 200-message burst. Batches are bounded to 500 messages. Rate-limited, oversized, unauthorized and storage-failed events are dropped rather than retrying indefinitely; counters and last receipt times are visible in Settings. These counters describe the current process run.

Default local retention is seven days, 100,000 events and an estimated 200 MB event/index budget. The first local limit reached removes oldest local records. Presets are 7 days, 1 month (30 days), 6 months (180 days), 12 months (365 days), and indefinite (no age deletion). The local size and event-count limits still apply to indefinite local retention. Configure 1,000–1,000,000 events and 10–2,000 MB in Settings. Database allocation can differ from estimated event bytes; incremental vacuum reclaims deleted pages. Two-second batch commits use the separate archive; read queries have a short busy timeout and a 250 ms SQLite progress budget. The app reports unavailable evidence if the archive is missing or busy.

`sudo docker compose logs --tail=50 log-receiver` shows listener/storage status without printing received messages or secrets. Docker reports unhealthy if the collector heartbeat stops. Include the event volume in backups if retaining history matters; existing operational backups do not automatically contain it. Standalone installations can run `python -m aiticket log-receiver --host 0.0.0.0 --port 5514`; `AITICKET_LOG_DATA` sets the archive path, otherwise it is next to `app.db`.

## Local and SMB storage tiers

Update normally with `git pull --ff-only origin main` and `sudo docker compose up -d --build`. Compose now starts **app**, **log-receiver**, and **log-archiver**. Keep deployment-specific volume mounts in `compose.override.yaml` so future updates do not conflict with tracked Compose changes. The archive service has read-only access to the existing encryption key; the syslog receiver does not need the key. No CIFS package, privileged container, host mount or manual share configuration is required.

In **Settings → Network logs → SMB log archive**, enter the server IP/hostname, share name, optional folder, username, password and optional domain. Select **Copy logs to this SMB archive**, choose an SMB retention period and click **Save and test connection**. The background test checks create, write, rename, read and delete permissions and displays its result on the same page. Invalid fields preserve entered non-secret values in a banner. Passwords are encrypted with the application's existing key, are never returned to the form, and are included in offline encryption-key rotation. Blank passwords retain the saved password only for the same server, share and account. SMB signing is required; SMB 3 encryption is optional.

Each incoming event commits to local history and, when mirroring is enabled and capacity permits, a durable upload queue in the same SQLite transaction. The queue survives restarts and has its own configurable estimated byte budget (default 256 MB; 16–16,384 MB). A separate worker compresses queue batches and writes them under:

```text
<share>/<optional folder>/aiticket-network-logs/<installation namespace>/<YYYY-MM-DD>/logs-....jsonl.gz
```

The active SQLite database stays local: [SQLite documents network-filesystem locking hazards](https://www.sqlite.org/useovernet.html). SMB stores immutable compressed JSON-line batches, with SHA-256 checksums encoded in filenames. Uploads use a temporary `.partial` file, read it back to verify its checksum, then rename to the completed filename before acknowledging queued events. Stable filenames make interrupted retries idempotent. Existing retained local history is copied in bounded batches on enable; changing the destination also copies currently retained local history to the new destination. Old SMB history is not moved or deleted during a destination change.

The first upload occurs promptly. Subsequent small batches normally wait at most five minutes; batches of 1,000 events upload sooner, with an 8 MB uncompressed batch ceiling. Failed SMB operations retry with backoff up to five minutes. No SMB operation runs in the collection loop or the HTTP request. Pending copies remain queued even after their local-history counterparts expire. If the queue fills, newer events can still be copied from local history while they remain there. If local limits expire those unqueued events, the archive-gap counter reports the loss; finite local buffers cannot guarantee unlimited outages. Lowering the upload-buffer limit can also discard older pending copies when no local copy remains. Budgets are estimates, not exact database allocation quotas.

SMB retention is independent of local retention and uses receipt time. Presets are 7, 30, 180, 365 days, or indefinite. Completed batches expire together once the newest receipt in the batch is outside the period. Indefinite SMB retention does not automatically delete completed batches. Retention manages only matching archive filenames in this installation's subfolder; unrelated share files are untouched. Pausing SMB also pauses its remote retention work; both resume on re-enable. Shortening retention deletes expired batches; raising it cannot recover already deleted logs. When the SMB disk is full or offline, local collection continues and the UI reports retry/backlog status.

## Search SMB history and recover after downtime

**Network events** searches the fast local tier. Choose **Search SMB history** to request a background search for any retained time range up to 31 days, with host, sender, severity, message/IP/MAC filters. Daily partitions and batch event-time bounds locate older or delayed observations. Searches return up to 200 unique events and explicitly mark partial results when batch, scan or result limits apply; timeouts show a failed search. Narrow the date range or filters to retrieve more. Current manual MAC bindings and maintenance context are applied to historical results; old IP ownership is not recomputed from current addresses. Search-result caches remain local for 24 hours or the latest eight completed searches (at most 64 MB plus one in-progress result). They are independent of SMB retention and can be searched again after expiry. Ordinary AI evidence queries use the local tier; authorized operational AI tools can request the bounded archive searches described above. Human archive searches remain available independently.

Completed SMB files, pending local uploads and configuration survive ordinary service restarts and temporary shutdowns. Preserve the **app-data**, **network-logs**, and **app-keys** volumes during updates. Back up the main database and encryption key as well: they hold the connection configuration, installation namespace, host/source associations and encrypted SMB credentials needed to reconnect to existing history. The SMB archive is an additional storage tier, not a backup of the application's settings or key. Events sent while the collector itself is stopped are not collected unless the sender buffers and retransmits them.

For archive diagnostics, use `sudo docker compose logs --tail=50 log-archiver`. Settings show the last verified upload, pending copies/buffer usage, unqueued local events, retry errors and archive gaps. Standalone Linux/macOS installations can run `python -m aiticket log-archiver` alongside the collector, using the same data path, key and `AITICKET_LOG_DATA`.

Connection failures distinguish DNS resolution, TCP port 445 timeouts/refusals, unreachable routes, server disconnects, authentication, denied file access, unsupported connection features and full storage. A TCP connection failure occurs before SMB authentication or share access; check connectivity from the `log-archiver` container to the selected SMB server before changing credentials. Error messages classify nested socket/SMB failures without exposing raw exception text, account names or paths.
